# The wacl runtime, extracted from the 2026-10-17 Bridge build

This folder holds the WebAssembly Tcl 9.1 runtime of the Bridge page as standalone files, decoded back from the base64 that the page embeds. Nothing was rebuilt and the page was not touched. The decoded bytes were compared with the files in `wacl/dist/` of the monorepo and are identical to them, and the same hashes are recorded in `PREBUILTS`, so these are the exact bytes the page carries.

One thing needs saying before the details, because it decides how the files can be used. The goal was two opaque blobs that another single-file app can inline without understanding the runtime. Two blobs are not enough on their own. The wasm module is not self-contained: its imports are supplied by a JavaScript glue file, `wacl.js` (124 KB of text, produced by the same Emscripten link), and the data file has no table of contents of its own, because Emscripten's file packager keeps the file index inside that glue file. So a host app has to carry three things, and none of them needs to be understood, only inlined and wired as described below: the wasm, the data file, and the glue. A second data file, `wacl-custom.data`, is requested by the glue as well; it holds only a 976-byte README and has to be supplied but does nothing.

## The files

`wacl.wasm` is 1,953,920 bytes, sha256 `4fac38243297ec0a4c9bceeefce025674b5456cb9d8964c22b05cba2ced31f77` (2,605,228 base64 characters). `wacl-library.data` is 627,760 bytes, sha256 `1b22165e69d19090beeeeb02904ea99a35750a1974cf7026ce97ed699ef239c3` (837,016 base64 characters); it is the Tcl 9.1 library and nothing else, mounted at `/usr/lib/` in the runtime's file system: `tcl9.1/` (the library scripts, including `tclIndex`) and `tcl9/9.0/` (the `.tm` modules http, msgcat, platform, platform::shell, tcltest). No tcllib and no encoding tables. `wacl-custom.data` is 976 bytes, sha256 `46874b6dfe04b9c693815fe904a52e3583260323857dee46ac7373c484e3b2f8`, a single file `/usr/lib/README`.

`wacl.js` is the glue, 123,996 bytes, sha256 `18de58207274d57e0176913079652273521789b0fdf05fde4404600eaaf70650`. It is a classic script (not a module). It contains the data files' index, the import table for the wasm, and the small public API (`wacl.onReady`, `interp.Eval`, `jswrap`).

Two further small files show how the Bridge page wires the three together. `wacl-loader-template.html` is the page's loader script exactly as `build.py` holds it, with `@@WASM_B64@@`, `@@LIB_B64@@` and `@@CUSTOM_B64@@` where the base64 goes. `wacl-ready.html` is the page's script that waits for the runtime. They are provided so that nobody has to reconstruct them; they are not part of the runtime.

## Where they came from

The build tree is `wacl-build/` of the bridge-wacl monorepo, your wacl-tcl9 build (upstream ecky-l/wacl at commit 9daacab, modernised for Tcl 9 and Emscripten 6) with the changes of 2026-10-17. The Tcl is 9.1.0 from `dl/tcl-core9.1.0-src.tar.gz` (sha256 `ba11ae7035ec4b0caf2c489b20d5aa2abb1cf001a7e65b0fa2fbac86908c643b`) with `wacl-build/patches/tcl-9.1.0-wacl.patch` applied (it adds the wacl objects to the Tcl makefile and forces the select notifier). These files were built on 2026-10-17 in the tree itself, at `/home/user/bridge-monorepo/bridge-wacl-monorepo/wacl-build`; the earlier prebuilts had been built at `/home/hatch/workspace/wacl-build/wacl-tcl9`, which is the path your own notes use. The absolute build directory is embedded in `wacl.js` and `wacl.wasm`, so a rebuild elsewhere gives different bytes for those two (the data files come out identical). Reproducibility here means the same pinned inputs, not the same bytes.

## Emscripten version and flags

Emscripten SDK 6.0.12 (emcc 6.0.12, emscripten-releases commit 6e9f6885cb17a3d6c8fd488a5cff730f50aba61d). Tcl was configured with `emconfigure ./configure --prefix=<build>/jsbuild --disable-load --disable-shared`, built with `emmake make`, and installed into `jsbuild/`. The data files were made with Emscripten's `file_packager.py`, `--preload library@/usr/lib/` and `--preload custom@/usr/lib/`, and the link was:

`emcc -Oz --pre-js preGeneratedJs.js --post-js js/postJs.js -s FORCE_FILESYSTEM=1 -sEXPORTED_FUNCTIONS=_main,_Wacl_GetInterp,_Wacl_TclEval,_Wacl_TclGetStringResult -sEXPORTED_RUNTIME_METHODS=ccall,cwrap,UTF8ToString,lengthBytesUTF8,stringToUTF8,addFunction,FS -s ALLOW_MEMORY_GROWTH=1 -s NO_EXIT_RUNTIME=1 -s STACK_SIZE=16777216 -s INITIAL_MEMORY=67108864 -s ALLOW_TABLE_GROWTH=1 libtcl9.1.a -o wacl.js`

where `preGeneratedJs.js` is `js/preJs.js` followed by the two file-packager loaders. No threads, no shared memory, no JSPI and no Asyncify in this module, so it runs in any browser with WebAssembly, from `file://`, with no special headers.

## Exported functions

The three C functions that the page uses are `Wacl_GetInterp()`, which returns the main interpreter pointer (an integer); `Wacl_TclEval(interp, script)`, which evaluates a string and returns the Tcl result code; and `Wacl_TclGetStringResult(interp)`, which returns the interpreter's current result as a string. `main` also is exported and runs at start-up (it creates the interpreter, calls `Tcl_Init`, then `Wacl_AppInit`, which registers the `wacl` package and `::wacl::jscall` and installs a trap on `exit` so that Tcl's `exit` never ends the page).

The raw wasm export names are minified by Emscripten, so the module cannot be called by those names without the glue. The mapping in this build is: `oa` the module's static initialiser (called once during runtime init), `pa` Wacl_TclEval, `qa` Wacl_TclGetStringResult, `ra` Wacl_GetInterp, `sa` main, `ta` htonl, `ua` htons, `va` ntohs, `wa` emscripten_builtin_memalign, `xa` malloc, `ya` stack restore, `za` stack alloc, `Aa` current stack pointer, plus the memory `na` and the function table `Ba`. The module imports 67 functions, all from the single module name `a`, supplied by the glue; it imports no memory (it defines and exports its own). Because the mapping changes with every link, use the glue's `Module._Wacl_TclEval` and friends, or the `wacl.onReady` API below, and never the minified names.

On top of the C functions, `wacl.js` offers the API that applications actually use: `wacl.onReady(cb)` calls `cb(interp)` once the runtime is up, and the object has `Eval(script)` (returns the result string, throws an object with `errorCode` and `errorInfo` on a Tcl error; it wraps the script in `catch`), `stdout` and `stderr` setters, `Module` (with `FS`, the Emscripten file system, usable from JavaScript), `str2ptr`/`ptr2str`, and `jswrap(fn, returnType, argType)`, which returns a Tcl command prefix that calls a JavaScript function (the return type must be `int`).

## Memory

The memory is defined by the module, not imported. Initial size 1024 pages, which is 64 MiB (`INITIAL_MEMORY=67108864`). Maximum 32768 pages, which is 2 GiB, with growth allowed (`ALLOW_MEMORY_GROWTH=1`). The stack is 16 MiB (`STACK_SIZE=16777216`) and is inside that initial memory. The function table can grow (`ALLOW_TABLE_GROWTH=1`), which `jswrap` uses. The memory is not shared.

## What the host must do before the first Eval

The runtime asks for its files by URL. The glue fetches the wasm with an `XMLHttpRequest` for `wacl/wacl.wasm` (response type arraybuffer) and the two data files with `fetch` or `XMLHttpRequest` for `wacl-library.data` and `wacl-custom.data` (relative to the page, with `filePackagePrefixURL` set to `wacl/`). A single-file app has no URLs, so the Bridge page installs a shim, before the glue runs, that answers those requests from memory. The steps, in order:

First, define a map from file name to base64 text (`window.__waclAssets = {"wacl.wasm": "...", "wacl-library.data": "...", "wacl-custom.data": "..."}`) and replace `window.fetch` and `window.XMLHttpRequest` with versions that return the decoded bytes when the requested URL ends with one of those names and pass every other request through. `wacl-loader-template.html` is that shim verbatim; its keys are matched by suffix, so the names must stay exactly `wacl.wasm`, `wacl-library.data` and `wacl-custom.data`. Second, put the text of `wacl.js` in a classic `<script>` after the shim. It removes `window.Module` and defines `self.wacl`, so there can be one runtime per page and it must be loaded as a plain script, not as a module. Third, call `wacl.onReady(function (interp) { ... })`. The callback is called after the runtime has started, which means after `main` has run `Tcl_Init` and `Wacl_AppInit`; there is no other initialisation step, and `interp.Eval("expr 6*7")` works inside the callback. If `wacl.onReady` is called before the script has run, it does not exist yet, so call it from a script that comes after, as `wacl-ready.html` does. Fourth, optionally route output: assign `interp.stdout = function (line) {...}` and `interp.stderr = ...` (otherwise Tcl's `puts` goes to the console), and set `interp.Module.waclOnExit = function (code) {...}` to be told about a trapped `exit`.

The glue starts `main` itself; the host never calls it. Everything is synchronous after that, on the page's main thread, so a long Tcl command blocks the page.

## What the Bridge page adds on top, and which of it you may want

None of this is needed for plain `Eval`. The page creates `/home/shell` in the file system (`interp.Module.FS.mkdirTree`), and it runs the shell in a child interpreter, which needs `::env(TCL_LIBRARY)` set to `$::tcl_library` before `interp create` (a new interpreter otherwise cannot find `init.tcl`) and the parent's `package unknown` handed down. In the bare runtime `::tcl_library` is `/usr/lib/tcl9.1` and `auto_path` is `/usr/lib/tcl9.1 /usr/lib` plus a stale build-time directory that does not exist at run time. `package require` works for packages with a `pkgIndex.tcl` under `auto_path`, but not for the `.tm` modules (http, msgcat, platform, tcltest), because Tcl's module finder is not active in this embedding; the Bridge page repairs that at boot with a three-line procedure, `::coreboot::pkgsetup` in `bridge/tcl/core.tcl`, which sources `$tcl_library/tm.tcl` and wraps `package unknown` with `::tcl::tm::UnknownHandler`. The library data deliberately contains no tcllib; the Bridge page supplies tcllib itself as a separate payload under `/core/vendor/tcllib` and adds it to `auto_path`. The runtime also has no sockets, no real processes (`exec` of an external program fails) and only the encodings built into Tcl.

## Inlining recipe for another single-file app

For a host build script that must not understand the runtime: base64 the three binary files (`wacl.wasm`, `wacl-library.data`, `wacl-custom.data`) into the asset map in the loader template, paste `wacl-loader-template.html` (with the three placeholders filled) and the text of `wacl.js` as two consecutive `<script>` elements, and follow them with a script that calls `wacl.onReady`. The total weight is about 3.4 MB of base64 plus the 124 KB glue. To change the Tcl library or the glue, rebuild with `./build.sh wacl` in the monorepo; for any other purpose the three binaries and the glue are opaque.
